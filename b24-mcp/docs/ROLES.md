# Роли и разрешения

## Три идентичности

| Роль | Кто это | Токен |
|---|---|---|
| `claude_sales_agent` | Универсальный sales-агент на Claude | `CLAUDE_MCP_TOKEN` |
| `codex_sales_agent` | Универсальный sales-агент на Codex | `CODEX_MCP_TOKEN` |
| `admin` | Человек-оператор: подтверждения, разбор HUMAN_REVIEW, отчёты | `ADMIN_MCP_TOKEN` (или `MCP_AUTH_TOKEN`) |

**Claude и Codex равноправны.** Ни один из них не является «продавцом», а
другой — «аудитором». Оба ведут активные оптовые продажи: ищут, квалифицируют,
считают lead score, готовят касания, заводят карточки, фиксируют звонки,
планируют следующие шаги. Набор возможностей задан одной константой
`SHARED_SALES_CAPABILITIES`, поэтому разойтись он не может — на это есть тест
(`tests/roles.test.ts`: «gives Claude and Codex an identical sales toolset»).

## Как определяется идентичность

- **stdio** — по переменной `AGENT_ID` процесса. Один процесс = один агент.
- **HTTP** — по `Authorization: Bearer <токен>`; сравнение constant-time по
  SHA-256-дайджестам, чтобы длина токена не утекала через тайминг.

Общий токен на двоих использовать нельзя: audit log и A/B-сравнение перестанут
различать авторов действий.

## Возможности

`SHARED_SALES_CAPABILITIES` (оба агента):

```
crm.read
crm.create_company · crm.create_contact · crm.create_deal
crm.add_note · crm.add_call_summary
crm.create_followup · crm.update_next_step
crm.propose_stage_change · crm.prepare_outreach
sales.claim · sales.release · sales.complete · sales.transfer
sales.own_metrics
```

`admin` дополнительно: `sales.all_metrics`, `sales.force_release`,
`sales.approve_risky`, `sales.ab_report`.

## Правила совместной работы

1. Один клиент или одна сделка одновременно закреплены ровно за одним агентом.
2. Захват атомарный: параллельные попытки завершаются одним победителем.
3. Агент не может менять запись, закреплённую за другим агентом (кроме `admin`).
4. Блокировка снимается автоматически через `ASSIGNMENT_LOCK_MINUTES`.
5. Передача — только с указанием причины.
6. Каждое действие пишется в audit log с actor, ролью, причиной и временем.
7. Бесконечная передача запрещена.
8. После `MAX_TRANSFERS` (по умолчанию 2) объект уходит в `HUMAN_REVIEW`.
9. Агент не подтверждает собственные рискованные изменения: `approved_by`
   обязателен и не может совпадать с автором.
10. Ограничения на удаление, цены, счета, массовые операции и отправку
    сообщений одинаковы для обоих агентов.

## Ограничения, общие для всех ролей

Даже `admin` через шлюз не может: удалить запись, вызвать произвольный
REST-метод, отправить сообщение клиенту, выставить счёт, изменить цену.
Массовые операции (> `MAX_WRITE_BATCH`) требуют подтверждения `admin`;
перевод сделки в проигрыш — подтверждения другой идентичностью.

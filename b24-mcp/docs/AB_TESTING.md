# Протокол A/B-сравнения: Claude против Codex

Цель — понять, какой агент лучше ведёт активные оптовые продажи. До накопления
статистики оба агента считаются равными, и шлюз этого не скрывает: отчёт
возвращает `winner: null`, пока условия не выполнены.

## Условия корректности

1. **Одинаковое количество клиентов.** Дисбаланс более 10% помечает
   эксперимент как невалидный (`balanced: false`).
2. **Сопоставимые сегменты и качество базы.** Распределение по бакетам —
   детерминированный SHA-256 от `entity_type:entity_id`, то есть не зависит от
   порядка обработки и не коррелирует с качеством карточки.
3. **Отсутствие пересечения компаний.** Одна компания принадлежит одной руке
   эксперимента. Пересечения перечисляются в `experiment.overlap`; пока список
   не пуст, вывод делать нельзя.
4. **Одинаковые разрешённые инструменты.** Гарантируется общей константой
   `SHARED_SALES_CAPABILITIES` и тестом на равенство наборов.
5. **Одинаковые лимиты.** `MAX_PAGE_SIZE`, `RATE_LIMIT_RPS`, call budget,
   `MAX_WRITE_BATCH`, правила подтверждений — общие.
6. **Единая методика оценки.** Метрики считаются из `agent_assignments`, а не
   из самоотчётов агентов.

## Запуск

```dotenv
AB_TEST_ENABLED=true
ROUTING_MODE=round_robin
ROUTING_MIN_SAMPLE=50
```

При `AB_TEST_ENABLED=true` захват чужого бакета отклоняется: агент не может
взять клиента из другой руки.

## Метрики

Из `sales_complete_assignment` и результата назначения:

| Метрика | Источник |
|---|---|
| Доля корректно квалифицированных | `1 − manual_corrections / completed` |
| Доля карточек без ошибок | `1 − (duplicates + manual_corrections) / completed` |
| Созданные следующие действия | `next_actions_created` |
| Конверсия в ответ | `replied / completed` |
| Конверсия в обсуждение заказа | `order_discussion / completed` |
| Конверсия в счёт | `invoice_issued / completed` |
| Конверсия в оплату | `paid / completed` |
| Ручные исправления | `manual_corrections` |
| Дубли | `duplicates_detected` |
| Опасные/отклонённые операции | `risky_operations_blocked` |
| Среднее время обработки | `avg_handling_seconds` |
| Стоимость обработки клиента | `cost_per_account` |
| Токены | `tokens_used`, `tokens_per_account` |

Ежедневный срез сохраняется в `data/agent_performance_daily.json`
(таблица `agent_performance_daily`: `date`, `agent`, счётчики, среднее время,
стоимость, токены).

## Порядок оценки

Победитель определяется строго по приоритетам, а не по объёму активности:

1. Оплаченные сделки.
2. Корректность CRM.
3. Конверсия в следующий этап.
4. Отсутствие рискованных действий.
5. Скорость и стоимость.

Первый критерий, где есть разница, определяет результат. Тест
`ranks by paid deals before activity volume` фиксирует, что агент с 500
созданными действиями и 2 оплатами проигрывает агенту с 10 действиями и
9 оплатами.

## Отчёт

```jsonc
{"name": "sales_get_agent_metrics",
 "arguments": {"agent": "claude_sales_agent", "include_comparison": true}}
```

Доступен только `admin`. Возвращает метрики, статус эксперимента
(выборка, баланс, пересечения) и сравнение. `winner: null` означает
«выборки не хватает» — это не ошибка.

## Когда включать performance_based

Только после того, как у **каждого** агента накопилось не менее
`ROUTING_MIN_SAMPLE` завершённых назначений и `ready_for_verdict: true`.
До этого момента режим автоматически откатывается к `round_robin` и объясняет
причину в `routing.reason`. Даже после включения распределение остаётся
взвешенным: отстающий агент продолжает получать примерно каждую третью задачу.

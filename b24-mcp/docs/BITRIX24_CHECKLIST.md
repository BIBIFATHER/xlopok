# Что нужно сделать руками в Битрикс24

Шлюз не создаёт ничего в портале самостоятельно. Пункты ниже выполняет человек.

## 1. Вебхук

1. Портал → **Разработчикам → Другое → Входящий вебхук**.
2. Права (scope): `crm`, `tasks`, `user`.
3. Скопировать URL вида `https://<portal>.bitrix24.ru/rest/<user_id>/<secret>/`
   в `.env` → `BITRIX24_WEBHOOK_URL`. В git не коммитить, в чат не вставлять.
4. Вебхук создавать от служебного пользователя с ограниченными правами на CRM,
   а не от администратора портала.

Проверка после подключения: `crm.item.fields`, `crm.status.list` — оба должны
отвечать без `insufficient_scope`.

### 1a. Права служебного пользователя

Вебхук работает в рамках прав своего пользователя. Проверить, что этот
пользователь видит нужные компании, контакты, сделки и задачи. `npm run
validate:live` фиксирует это в блоке `rights`: id пользователя, доступность
scope `crm` (`crm.item.fields`) и scope `tasks` (`tasks.task.field.list`).
Если `tasks.task.field.list` отвечает `insufficient_scope` — у вебхука нет
права `tasks`, задачи работать не будут.

### 1b. Диалект задач (TASKS_API_MODE)

`tasks.task.list` в Битрикс24 существует в двух вариантах:

- **legacy** — классический контракт вебхука: объектный фильтр с префиксами
  (`@STATUS`, `<DEADLINE`), пагинация через `start`, строки в ключе `tasks`;
- **v3** — REST v3 endpoint `…/rest/api/<user>/<token>/tasks.task.list`:
  фильтр массивом условий `["field","op",value]`, объект `pagination`
  (`limit`/`offset`), строки в `result.items`.

Какой из них отвечает — свойство конкретного портала. **Не выбирать вслепую.**
Запустить `npm run validate:live`, посмотреть блок `tasks_api` в отчёте
(`confirmed_mode`) и выставить `TASKS_API_MODE` в подтверждённое значение.
По умолчанию — `legacy`.

## 2. Пользовательские поля Canvas Lab

Коды `UF_CRM_*` выдаются порталом при создании — **их нельзя выдумать**.
Порядок: создать поле → узнать код через `crm.item.fields` → внести в
`FIELD_MAP_COMPANY` / `FIELD_MAP_DEAL`.

### Компания

| Доменное имя | Название поля | Тип |
|---|---|---|
| `segment` | Сегмент | Список (багетная мастерская / художественный салон / сеть / опт / маркетплейс) |
| `city` | Город | Строка |
| `website` | Сайт | Ссылка |
| `number_of_locations` | Количество точек | Число |
| `sales_channels` | Каналы продаж | Список, множественное |
| `current_supplier` | Текущий поставщик | Строка |
| `estimated_monthly_volume` | Оценка объёма, шт/мес | Число |
| `canvas_assortment` | Ассортимент холстов | Список, множественное |
| `price_segment` | Ценовой сегмент | Список (эконом / средний / премиум) |
| `lead_score` | Lead score | Число |
| `data_quality` | Качество данных | Список (high / medium / low) |
| `verification_status` | Статус верификации | Список (не проверен / проверен / отклонён) |
| `last_meaningful_contact_at` | Последний значимый контакт | Дата |
| `next_expected_purchase_at` | Ожидаемая следующая закупка | Дата |

### Сделка

| Доменное имя | Название поля | Тип |
|---|---|---|
| `need` | Потребность | Текст |
| `interested_sizes` | Интересующие размеры | Список, множественное |
| `estimated_quantity` | Оценка количества | Число |
| `estimated_revenue` | Оценка выручки | Деньги |
| `price_sent_at` | Прайс отправлен | Дата |
| `samples_sent_at` | Образцы отправлены | Дата |
| `next_step` | Следующий шаг | Строка |
| `next_step_at` | Срок следующего шага | Дата |
| `loss_reason` | Причина проигрыша | Список |
| `ai_summary` | Резюме AI | Текст |
| `ai_confidence` | Уверенность AI | Число (0–1) |

Пример заполнения после создания полей:

```dotenv
FIELD_MAP_COMPANY={"segment":"UF_CRM_1700000001","estimated_monthly_volume":"UF_CRM_1700000002"}
FIELD_MAP_DEAL={"next_step":"UF_CRM_1700000101","loss_reason":"UF_CRM_1700000102"}
```

Незамапленные поля просто не используются: инструмент вернёт список
пропущенных, но ничего не сломает.

## 3. Воронка и стадии

1. Проверить воронку оптовых продаж и коды стадий (`crm.dealcategory.stage.list`).
2. Убедиться, что финальные стадии начинаются с `WON` / `LOSE` / `APOLOGY` —
   на этом основано определение открытых и проигранных сделок.
3. Заполнить справочник причин проигрыша для поля `loss_reason`.

## 4. Пользователи и права

1. Завести (или выбрать) ответственных менеджеров — их ID нужны для фильтров
   и постановки задач.
2. Проверить, что служебный пользователь вебхука видит нужные сделки: шлюз
   работает в рамках прав этого пользователя.

## 5. Перед включением записи

- [ ] Поля из п. 2 созданы, коды внесены в `.env`.
- [ ] Стадии и причины проигрыша согласованы.
- [ ] Проверено на тестовом портале, что dry-run diff соответствует ожиданиям.
- [ ] Определён ответственный по умолчанию для новых карточек.
- [ ] Настроено резервное копирование портала.
- [ ] Только после этого — `WRITE_ENABLED=true` на тестовом портале.

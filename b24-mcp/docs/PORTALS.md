# Подключение тестового и боевого портала

Порядок жёсткий: тестовый портал → чтение → запись на тесте → боевой портал
в read-only → запись на бою.

## Этап 1. Тестовый портал, только чтение

```dotenv
BITRIX24_WEBHOOK_URL=https://<test-portal>.bitrix24.ru/rest/<user>/<secret>/
WRITE_ENABLED=false
LOG_LEVEL=debug
DATA_DIR=data/test
```

Проверка:

```bash
npm run build && TRANSPORT=http npm start &
curl -s http://127.0.0.1:8787/health | jq '.config'   # writeEnabled: false
```

Контроль: `tools/list` не содержит ни одного `crm_create_*` / `crm_update_*`.

## Этап 2. Тестовый портал, запись

Только после выполнения `BITRIX24_CHECKLIST.md`.

```dotenv
WRITE_ENABLED=true
FIELD_MAP_COMPANY={...}
FIELD_MAP_DEAL={...}
```

Правила этапа:

- каждая операция сначала с `dry_run: true`, diff читает человек;
- партии не больше нескольких карточек;
- после каждой партии — просмотр `data/audit/audit.jsonl` и `dead-letter.jsonl`.

## Этап 3. Боевой портал, только чтение

1. Отдельный вебхук от служебного пользователя с ограниченными правами.
2. `WRITE_ENABLED=false`, `DATA_DIR=data/prod`, `LOG_LEVEL=info`.
3. Прогнать `crm_get_sales_summary`, `crm_get_overdue_followups`,
   `crm_get_deals_without_next_action` — цифры сверить с интерфейсом портала.
4. Минимум неделя работы агентов в этом режиме.

## Этап 4. Боевой портал, запись

Условия включения:

- [ ] Резервное копирование портала настроено и проверено восстановлением.
- [ ] Пользовательские поля созданы, `FIELD_MAP_*` заполнены.
- [ ] На тесте выполнено не менее 50 операций записи без инцидентов.
- [ ] Audit log просматривается регулярно, dead-letter queue пуста.
- [ ] Согласовано, кто выступает `admin` для подтверждений.
- [ ] A/B-эксперимент, если запускается, настроен по `AB_TESTING.md`.

Включение — отдельным решением человека, не по инициативе агента.

## Разделение окружений

| Параметр | Тест | Бой |
|---|---|---|
| `DATA_DIR` | `data/test` | `data/prod` |
| Токены агентов | отдельные | отдельные |
| `LOG_LEVEL` | `debug` | `info` |
| `AB_TEST_ENABLED` | можно | только по решению |

Один и тот же `DATA_DIR` для двух порталов использовать нельзя: назначения и
метрики смешаются.

## Откат

1. `WRITE_ENABLED=false` и перезапуск — write-инструменты исчезают немедленно.
2. При компрометации вебхука: отозвать его в портале, выпустить новый,
   обновить `.env`. Токены агентов перевыпустить независимо.
3. Ошибочные изменения разбираются по `audit.jsonl`: там есть actor, роль,
   diff и время каждой операции.
